The problem

Coverlay has 13 tables today. They were built for one job: analyse a resume, then suggest roles and jobs. The next features keep far more about each person, and some basics are missing.

No way to leave

There is no "Delete my account" button. If we delete a user by hand, the database removes their rows (every table cascades from users), but their uploaded resume files stay in storage.

No record of agreement

We don't store which Terms or privacy policy a person accepted, or when.

No idea who has gone quiet

We never record when someone last used Coverlay, so a two-year-old account is treated like yesterday's.

Applications hide inside saved jobs

A saved job has a status (Saved, Applied, Interview, Offer, Rejected) but no portal, no application id, no dates and no link to the resume that was sent.

No analytics

We can't see where people get stuck, which Lay AI requests fail, or which templates they pick.

More personal data is coming

The Resume Builder keeps every version and every Lay AI chat. The Lay AI agent will know where people apply.

The law asks for this too. India's Digital Personal Data Protection Act 2023 (DPDP), the EU's GDPR and California's CCPA all give people the right to see their data, correct it and have it erased, and they expect a company to report data breaches. Coverlay is meant for all three regions.

The goal: a clear list of what we keep and why, a life cycle for every account, a deletion that removes everything personal, and analytics that never point back to a person.

The idea

Think of Coverlay as a hotel

The hotel

A good hotel knows exactly what it holds for each guest. At check-in the guest is written in the register and signs the house rules. Their things go in a locker in their room. Letters they send go through the front desk, which keeps a mail log.

The manager keeps a tally book of what happens in the hotel, but writes ticket numbers in it, never names. The list that matches tickets to rooms sits in a sealed envelope.

When a guest checks out for good, the room is cleared, their page is torn out of the register and the envelope is burned. The tallies stay, and nobody can tell whose they were.

Step 1

What we store, and why

The hotel

At check-in the front desk writes down only what it needs to look after the guest: a name to call them by and a key that opens their door. The guest's things stay in their own locker.

The desk never keeps a copy of the guest's bank card, never reads their letters and never sells the guest list. Everything the hotel holds has a reason to be there and a day it leaves.

In Coverlay

We keep only what a feature needs, and every kind of data has a purpose, a place and a time limit. Passwords are stored as bcrypt hashes: a one-way scramble that can be checked but never read back.

Uploaded files live in object storage (MinIO, bucket resumes), filed under the user's id. Everything else lives in PostgreSQL.

What we never store

  • Plain-text passwords
  • Payment card details (Coverlay has no payments)
  • Passwords for LinkedIn, Naukri or any other site
  • Resume text, chat text, names, emails or phone numbers in usage events
  • Keystrokes, mouse paths or screen recordings
  • Precise location

Resume text and chat messages are sent to Gemini on Google's Vertex AI to do the work. Our ML service keeps the last 256 AI answers in memory so it doesn't pay twice for the same resume. That memory is cleared on every restart and never written to disk.

Step 2

Active and inactive accounts

The hotel

The front desk notes the last day it saw each guest. A guest who hasn't been around for a while keeps their room and their things, but the hotel stops slipping notes under their door.

If a room has stood unused for a very long time, the hotel writes to the guest's home address: "Your room will be cleared in 30 days unless you drop by." If the guest turns up, everything carries on. If not, the room is cleared exactly as at a final check-out.

In Coverlay

Each account gets a status and a last_active_at date, updated at most once a day when the user signs in or uses the app.

  • After 90 days without use the account becomes INACTIVE. Data stays; reminders and Lay AI nudges stop.
  • At 18 months it becomes DORMANT_NOTICE and we email the user a deletion date 30 days away.
  • Any sign-in moves it back to ACTIVE. If nothing happens, the nightly job deletes it the same way as a deletion the user asked for (Step 3).

Step 3

Deleted accounts

The hotel

A guest who wants to leave for good tells the front desk. The desk first offers a copy of everything in their locker to take home. Their key stops working at once, and the hotel holds their things for 14 days in case they change their mind.

After that the locker is emptied and shredded, their page is torn out of the register, and the sealed envelope with their ticket number is burned. The copies of the register kept in the safe are shredded within a month. The check-out ledger records only that a guest left that day.

In Coverlay

Settings get two buttons: Export my data (a ZIP with every record as JSON, plus the uploaded files) and Delete my account (confirmed with the password).

Deleting sets status = DELETION_PENDING and increases token_version, which makes every existing JWT invalid, so every device is signed out. Signing in within 14 days offers "Keep my account". After that, the nightly purge job runs these steps:

  1. Delete the files. Remove everything under <userId>/ in object storage. Today this step is missing: the cascade below doesn't reach storage.

  2. Delete the users row. Every table that points to users is set to ON DELETE CASCADE, so resumes, profiles, matches, feedback, saved jobs, the watchlist, Builder versions, chats, applications, reminders, consents and bug reports go with it.

  3. Cut the analytics link. The user_analytics_link row goes in the same cascade. Old usage events stay, but their subject_id no longer leads to anyone.

  4. Record the deletion. Write one row to deleted_accounts: a random id, the date and the reason (user request, inactivity or admin). No email, no user id.

  5. Let backups expire. Database backups are kept for 30 days, so the last copy of the account is gone within 30 days.

What stays after an account is deleted

Totals and anonymous events

"312 resumes analysed on 3 Nov", and events whose random id now points nowhere.

Learned skill weights

Numbers about roles that feedback helped tune. They describe roles, not people.

Public GitHub issues

Issues made from approved bug reports. They never contained the reporter's email.

Deleting a single resume version works the same way on a small scale: the file in storage and its rows go together.

Step 4

Where people apply

The hotel

When a guest wants to send a letter, the concierge can write the draft, address the envelope and leave it on the desk, ready to go. Only the guest drops it in the post box.

The front desk keeps a mail log: who each letter went to, the date, and the reference number on any reply. If a ready letter has sat on the desk for a few days, the concierge slips one note under the door, once, and only if the letter still hasn't been posted.

In Coverlay

A new job_applications table tracks each application from preparation to result. Lay AI may prepare one (a tailored resume version and the link to the portal) but never submits it: the user applies on the company's site, then marks it as applied.

saved_jobs stays as the bookmark list. Starting an application from a saved job creates a job_applications row.

The one reminder

The reminders table holds at most one FORGOT_TO_APPLY reminder per prepared application, due 3 days after it was prepared. It shows inside the app the next time the user opens it. It never goes out by email or phone notification unless the user turned that on, and it is dropped as soon as the application is marked applied. Columns: application_id, kind, due_at, shown_at, acted_at, dismissed_at.

Step 5

How analytics works

The hotel

The manager wants to know which parts of the hotel guests enjoy and where they get lost. Each guest gets a ticket number at check-in, picked at random. The tally book only ever says things like "ticket 4821 used the gym" or "ticket 4821 asked the concierge for directions".

The list matching tickets to rooms sits in a sealed envelope that only the front desk can open. Guests who would rather not be counted tick a box, and their ticket is never written down. Each night the manager adds up the day's marks. Old marks are thrown out after a year; the nightly totals are kept.

In Coverlay

Each account gets a random subject_id at sign-up. It is generated, not derived from the email or user id: a hash of an email can be reversed by guessing emails.

The only link between the two is the user_analytics_link table, which only the backend's analytics writer reads. Events go to a separate analytics schema with its own database role that cannot read users.

Each event name has an allowlist of details; anything else is dropped, and no event carries free text. A nightly job rolls events up into daily_metrics. Users can switch analytics off in Settings.

The most common Lay AI requests, without reading anyone's chat

Chat text stays in the user's own chat history. For analytics we record only Lay AI's own decision about what the request was (its intent: add_skill, remove_skill, shorten_summary, rewrite_summary or unknown) and the domain. prompt_stats counts these per day. The unknown count shows what Lay AI should learn to do next.

Step 6

Our duties to users

The hotel

A hotel owes its guests more than a bed. The doors lock and the safe is a real safe. Staff use a guest's things only to serve that guest, never read their letters and never sell the guest list.

A guest can ask to see what the hotel holds about them, fix a mistake, or take everything and leave. The house rules are written plainly and signed at check-in. A named person at the desk handles complaints. After a break-in, the hotel tells its guests and the police straight away. Children check in only with a parent.

In Coverlay

These duties come from DPDP, GDPR and CCPA, and from what users would expect of a careers app. Each one below is a feature or a rule we have to build and keep.

Keep it safe

  • bcrypt password hashes; HTTPS only (Caddy in front)
  • Disks and backups encrypted at rest (Google Cloud does this by default)
  • Least-privilege service accounts: the app account can only call Vertex AI and read models
  • Secrets in deploy/.env, never in git
  • Production data reached only by named admins, and every admin action logged

Use data only for what we said

  • Resume and chat data used only to analyse, build, match and track for that user
  • Never sold
  • Never shared with employers or recruiters unless the user sends it
  • Not used to train our own models without a separate opt-in

Be clear about AI

  • Gemini on Vertex AI reads resume text and chat messages to do the task
  • Google Cloud's terms say this data isn't used to train Google's models; check the current Vertex AI data-governance terms before launch
  • Lay AI never applies, never contacts recruiters, and reads only the signed-in user's own data

Give users control

  • See and export everything
  • Correct anything
  • Delete any version, any chat, or the whole account
  • Change any consent at any time; switch analytics off

Tell the truth

  • A plain-language privacy notice and Terms; the accepted version stored
  • Notice before either changes
  • After a breach, tell the affected users and the regulators quickly (GDPR: the authority within 72 hours; India: the Data Protection Board and the users)

Answer complaints

  • A named privacy contact and email address, shown in the privacy notice (DPDP asks for a grievance contact)
  • A reply within a stated time

Protect children

  • DPDP requires verifiable parental consent for anyone under 18, and many students are under 18
  • Proposal: sign-up asks users to confirm they are 18 or older; a parental-consent flow comes later

This is a product design, not legal advice. Have a lawyer review the privacy notice, the Terms and these retention numbers before real users sign up.

ALTER TABLE users
    ADD COLUMN status                VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE, INACTIVE, DORMANT_NOTICE, DELETION_PENDING
    ADD COLUMN last_active_at        TIMESTAMPTZ NOT NULL DEFAULT now(),

    ADD COLUMN token_version         INTEGER     NOT NULL DEFAULT 0;       -- +1 signs out every device

CREATE TABLE user_consents (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    kind       VARCHAR(30) NOT NULL,   -- TERMS, PRIVACY, ANALYTICS, EMAIL_REMINDERS
    version    VARCHAR(20) NOT NULL,   -- e.g. '2026-11'

    decided_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE job_applications (
    id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id                 UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    job_posting_id          UUID REFERENCES job_postings(id) ON DELETE SET NULL,
    company_name            VARCHAR(255) NOT NULL,
    role_title              VARCHAR(255) NOT NULL,
    portal                  VARCHAR(20)  NOT NULL,          -- COMPANY_SITE, LINKEDIN, NAUKRI, OTHER
    external_application_id VARCHAR(120),
    resume_version_id       UUID,                          -- -> resume_document_versions(id)
    status                  VARCHAR(20)  NOT NULL DEFAULT 'PREPARED',
    prepared_at             TIMESTAMPTZ  NOT NULL DEFAULT now(),
    applied_at              TIMESTAMPTZ,
    status_changed_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
    notes                   TEXT
);

CREATE TABLE user_analytics_link (
    user_id    UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    subject_id UUID NOT NULL UNIQUE                 -- random, made at sign-up
);

CREATE SCHEMA analytics;
CREATE TABLE analytics.events (
    id          BIGSERIAL PRIMARY KEY,
    subject_id  UUID        NOT NULL,                 -- no foreign key to users, on purpose
    name        VARCHAR(60) NOT NULL,
    properties  JSONB       NOT NULL DEFAULT '{}',     -- allowlisted keys only, no free text
    client      VARCHAR(10) NOT NULL,                 -- web, phone
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Spring Boot: the nightly purge and the event recorder

@Component
public class AccountPurgeJob {

    private static final Duration GRACE = Duration.ofDays(14);

    // Every night at 03:15 India time.
    @Scheduled(cron = "0 15 3 * * *", zone = "Asia/Kolkata")
    @Transactional
    public void purge() {
        Instant cutoff = clock.instant().minus(GRACE);
        for (User user : users.findByStatusAndDeletionRequestedAtBefore(UserStatus.DELETION_PENDING, cutoff)) {
            storage.deleteAllFor(user.getId());                  // files under "<userId>/"
            users.delete(user);                                   // cascades, incl. user_analytics_link
            deletedAccounts.save(DeletedAccount.of(Reason.USER_REQUEST, clock)); // no email, no user id
        }
    }
}

@Service
public class AnalyticsService {

    public void record(User user, String event, Map<String, Object> details, Client client) {
        if (!consents.allowsAnalytics(user)) {
            return;                                               // switched off: nothing is written
        }
        Map<String, Object> safe = catalogue.allowedDetails(event, details); // unknown keys dropped
        UUID subject = links.subjectFor(user);                    // the random id from sign-up
        events.insert(subject, event, safe, client);
    }
}
